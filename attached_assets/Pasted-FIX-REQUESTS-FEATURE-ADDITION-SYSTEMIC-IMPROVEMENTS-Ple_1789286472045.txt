=== 3. BUG: silent direction hardcoding instead of review_required ===

When I asked for a strategy where the 5m entry direction should be inherited
from a 1h Break of Structure bias condition (i.e. "make the Liquidity Sweep
and Displacement match whatever direction the 1h bias currently is"), the
resolver silently hardcoded both conditions to bearish polarity and displayed
the strategy-level Direction as "both" — producing a draft that looked like it
fulfilled the request but actually only ever represents one fixed direction.

Since direction cannot currently be dynamically inherited from another
condition's outcome (confirmed unsupported), any request that implies this
must instead mark the affected conditions as `review_required`, with a reason
such as: "direction cannot be dynamically linked to another condition's
outcome — this concept currently requires a fixed direction per condition."
Do not guess or silently default to one direction.

Add a regression test: a prompt requesting bias-dependent/inherited direction
across two conditions must return review_required with an accurate reason, and
must NOT return an executable draft with one direction silently chosen.

=== 6. FEATURE: direction inheritance between conditions (direction_from) ===

Add a new relationship type, `direction_from`, allowing a target condition's
direction/polarity to be resolved dynamically from a source condition's
outcome at evaluation time, instead of being fixed when the strategy is
created.

Example: "1h Break of Structure as bias, 5m Liquidity Sweep and Displacement
should match the 1h bias direction" should produce:
- 1h Break of Structure: direction = both (detects either bullish or bearish)
- 5m Liquidity Sweep + Displacement: direction = inherited via direction_from,
  source = the Break of Structure condition

Backtesting: at each candle, evaluate the source condition's most recently
established direction (bullish or bearish bias). Only evaluate the target
condition using that current direction. If the source condition has not yet
established a bias, the target condition must not fire in either direction.

Monitoring: identical mechanism — track the most recent source-condition
direction as persistent state, and only evaluate the target condition against
that current direction, updating whenever the source flips.

This must combine correctly with:
- existing FOLLOWED_BY temporal ordering (both relationship types may apply to
  the same condition pair simultaneously)
- existing cross-timeframe maxBarsBetween logic (see item 5 above — the
  regression test for that should exist before or alongside this feature)

Implement generically via registry metadata (e.g. a flag like
`producesDirectionalOutcome: true` on concepts such as Break of Structure,
Change of Character, Market Structure Shift, HTF Structure), NOT hardcoded to
one specific concept name.

Add regression tests:
A. Source bullish → target only fires bullish, never bearish, until source flips.
B. Source bearish → target only fires bearish.
C. Source has not fired yet → target never fires in either direction.
D. Source flips mid-sequence → target correctly switches direction from that
   point forward.
E. Cross-timeframe case (1h source, 5m target) combined with direction_from
   AND maxBarsBetween ordering — confirm both constraints apply together.
F. direction_from combined with an explicit prohibition elsewhere in the same
   prompt (e.g. "do not use EMA") — confirm no interference.

=== 7. SYSTEMIC IMPROVEMENT: fail loud, not silently plausible ===

Several of the bugs above (items 2-4) share a root cause: when the resolver
can't fully satisfy a request, it has been producing a draft that LOOKS
complete and correct rather than surfacing that something was assumed,
dropped, or approximated. This needs a structural fix, not three separate
patches.

Add a validation/audit pass that runs on every generated draft, BEFORE it's
shown to the user, checking for known "silent failure" shapes:

- A condition stage (Entry/Confirmation/Exit) that a strategy's structure
  would normally require is empty when concepts were actually detected and
  categorized elsewhere (as in item 2) — flag this as a structural warning,
  not a silent pass.
- A requested risk rule (SL/TP/R:R) that was mentioned in the user's request
  but does not appear in the final resolved risk rules — flag as a warning:
  "You requested a risk-reward rule but it did not resolve. Reason: [X]" —
  rather than just omitting it with no explanation.
- A condition whose direction/polarity was set to a specific fixed value
  (long/short) when the user's phrasing implied it should be derived,
  conditional, or dynamic — flag as review_required (per item 3) rather than
  silently picking one.
- Any other case where the resolver had to make an assumption not explicitly
  and unambiguously stated by the user (e.g. applying a default parameter
  value, defaulting an unspecified window like maxBarsBetween) — these are
  fine to apply, but must be visibly surfaced in the draft UI (as you already
  do correctly for "within 20 bars (default)"), not buried only in raw
  parameter JSON that a non-technical user won't read.

The goal: every assumption or gap gets surfaced in the draft summary users
actually look at (the top-level card, not just the expanded Review Strategy
view), so nothing that would materially change the user's decision to
create/backtest the strategy is invisible.

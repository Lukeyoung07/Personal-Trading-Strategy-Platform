TRADEX — COMPLETE TRADING CONCEPT LIBRARY KNOWLEDGE & VARIATION SYSTEM

I want to make the Trading Concept Library the single source of truth for
every trading concept in TradeX.

The current system has repeatedly confused concepts, created incorrect
conditions, and marked things Review Required because Build with AI does not
have a sufficiently complete understanding of the concepts already present
in the library.

Do NOT solve this by adding instructions to individual strategy prompts.

Fix the underlying Trading Concept Library and its canonical concept
definitions so Build with AI, Builder, Backtesting and Monitoring all use
the same definitions.

==================================================
PRIMARY OBJECTIVE
==================================================

Every concept currently present in the Trading Concept Library must have a
complete, machine-readable canonical definition.

For EVERY concept, define:

1. Canonical concept name
2. Definition
3. What the concept IS
4. What the concept IS NOT
5. All supported directional variations
6. All supported terminology/aliases
7. All supported parameter variations
8. Default parameters
9. Required parameters
10. Optional parameters
11. Required market data
12. Required timeframe
13. Whether it can be evaluated on closed candles
14. Exact executable conditions
15. Exact invalidation conditions where applicable
16. How it should behave in historical backtesting
17. How it should behave in live monitoring
18. How Build with AI should recognize it
19. How Build with AI should NOT interpret it
20. Which concepts are compatible with it
21. Which concepts must remain separate
22. Whether it is executable or review-required
23. Why it is executable or why it currently requires review
24. The canonical structured representation used by the rule engine

==================================================
VERY IMPORTANT — ALL VARIATIONS
==================================================

Do not define concepts only for their simplest wording.

For every concept, identify every reasonable variation that can be
deterministically represented by the existing concept.

For example:

"Liquidity Sweep"

must understand variations such as:

- bullish liquidity sweep
- bearish liquidity sweep
- buy-side liquidity sweep
- sell-side liquidity sweep
- sweep of previous high
- sweep of previous low
- sweep of a recent high
- sweep of a recent low
- wick through liquidity and close back inside
- close through liquidity and reclaim
- explicit lookback values
- previous candle liquidity
- previous day liquidity where supported
- previous week liquidity where supported

But DO NOT invent variants that the evaluator cannot actually execute.

The canonical definition must clearly distinguish supported variations from
unsupported ones.

==================================================
DIRECTIONAL VARIATIONS
==================================================

Where applicable, every concept must explicitly support:

- bullish
- bearish
- long
- short
- automatic/neutral where appropriate

Do not create separate fake concepts when one canonical concept with a
direction parameter is more appropriate.

For example:

Bullish Displacement
Bearish Displacement

should map to:

Displacement
direction = bullish/bearish

Likewise:

Bullish FVG
Bearish FVG

should map to:

FVG
polarity = bullish/bearish

Build with AI must understand both the canonical name and natural-language
variants.

==================================================

For every concept create an explicit alias map.

Examples:

"EMA 20 crosses below 50"
→ EMA Cross(fast=20, slow=50, direction=cross_below)

Do this comprehensively for EVERY concept in the library.

Do not rely on vague semantic similarity alone.

==================================================
DO NOT MERGE DISTINCT CONCEPTS
==================================================

Related concepts must remain distinct.

Examples:

FVG ≠ FVG Retest

FVG Retest ≠ FVG Fill

Liquidity Sweep ≠ Breakout

Breakout ≠ Failed Breakout

Displacement ≠ Momentum

BOS ≠ CHoCH

MSS ≠ BOS

EMA ≠ EMA Cross

RSI ≠ RSI Divergence

Divergence ≠ SMT Divergence

Order Block ≠ Order Block Retest

Support ≠ Support Retest

Resistance ≠ Resistance Retest

Do not map one concept to another simply because the concepts are commonly
used together.

==================================================
CONCEPTS USED TOGETHER
==================================================

The system must understand that strategy authors commonly combine concepts
without one concept becoming part of another.

For example:

"bearish liquidity sweep followed by bearish displacement"

contains TWO concepts:

1. Liquidity Sweep
2. Displacement

Do not convert this into one invented concept.

Likewise:

"bullish displacement followed by FVG retest"

contains:

1. Displacement
2. FVG
3. FVG Retest

The relationship/order between them should be represented separately from
the individual concept definitions.

==================================================
TEMPORAL RELATIONSHIPS
==================================================

Preserve explicit relationships such as:

- after
- followed by
- before
- then
- during
- while
- within
- immediately after

as strategy relationship metadata.

Do NOT silently turn a temporal relationship into a new trading concept.

Example:

"Displacement followed by FVG retest"

means:

Displacement
THEN
FVG Retest

It does not mean that "Continuation" or another concept should be
invented.

If the current rule engine cannot execute a particular temporal relationship,
preserve the relationship explicitly and report that specific limitation.

Do not replace it with a different rule.

==================================================

Build with AI must use the Trading Concept Library as its source of truth.

The process must be:

USER REQUEST
↓
CONCEPT EXTRACTION

↓
RESOLVE ALIASES / VARIATIONS
↓

↓

↓

BUILDER

The library definition wins.

If the user writes:

"bullish FVG"

polarity = bullish

It should not invent another concept.

TradeX — Fix Build with AI Strategy Generation and Builder Mapping

Audit and fix the existing “Build a Strategy with AI” pipeline.

The problem to fix is generic, not specific to one strategy:

When the user explicitly requests a simple executable strategy, the AI draft can incorrectly add unrelated unsupported concepts or risk rules.

For example, a request for:

- XAUUSD
- 5m
- Both directions
- EMA 20 cross only

incorrectly produced review-required items such as:
- Higher-timeframe bias
- SMT Divergence
- AMD / Power of 3
- Stop Loss
- Take Profit
- Generic risk rules

This must be fixed at the AI-to-Builder mapping/normalization layer so future strategies behave correctly.

IMPORTANT:

- Do NOT hard-code a fix specifically for XAUUSD.
- Do NOT hard-code a fix specifically for EMA.
- Do NOT hard-code a fix for this exact prompt.
- Do NOT rebuild the Strategy Builder.
- Preserve all existing executable concepts.
- Preserve all existing AI strategy-generation functionality.
- Preserve unsupported/review-only concept handling.
- Preserve existing Strategy → Version → Backtesting behaviour.
- Do not invent conditions the user did not request.
- Do not automatically add stop loss, take profit, risk rules, higher-timeframe bias, SMT, AMD/PO3, or other conditions unless the user's request explicitly asks for them.

1. AUDIT AI STRATEGY GENERATION

Trace the complete pipeline:

User prompt
→ AI interpretation
→ generated strategy draft
→ concept normalization
→ Builder condition mapping
→ strategy creation
→ immutable version

Identify where unintended conditions are being introduced.

2. USER INTENT MUST BE PRESERVED

The AI should only create conditions that are actually requested or clearly required to express the requested strategy.

If the user says:

“Use EMA 20 crossing only”

the generated strategy must not add:
- HTF bias
- SMT
- AMD/PO3
- FVG
- liquidity
- stop loss
- take profit
- confirmation conditions
- other concepts

unless explicitly requested.

3. SUPPORTED CONCEPTS

Use the existing canonical executable concept registry/normalization system.

Do not create a second hardcoded list.

If a requested concept is executable:
- map it to its canonical concept
- preserve its parameters
- assign the correct stage
- assign the correct direction
- assign the requested timeframe

If a requested concept is unsupported:
- preserve it as explicitly review-required
- explain why
- do not silently replace it with another concept.

4. RISK RULES

Do not invent risk rules.

If the user does not request:
- stop loss
- take profit
- trailing stop
- risk/reward
- position sizing

then leave risk-management rules unset.

Do not allow generic AI-generated text such as “risk rules” to create actual risk conditions.

5. DIRECTION

Correctly map:

Long
Short
Both

For “Both”, create the appropriate long and short executable conditions only when the requested rule supports directional mapping.

Do not invent additional directional filters.

6. TIMEFRAMES

Only use timeframes explicitly requested by the user.

For example:

“5m EMA strategy”

must remain 5m.

Do not introduce 1H, 4H, or other higher/lower timeframes unless requested.

7. STAGES

Correctly distinguish:

- Entry
- Confirmation
- Exit

Do not automatically convert a single requested entry rule into multiple conditions.

If the user asks for one entry condition, create one entry condition.

8. PARAMETERS

Ensure structured parameters survive:

AI interpretation
→ normalized draft
→ Builder
→ strategy creation
→ immutable v1
→ backtesting
→ monitoring

Do not lose or invent:
- EMA period
- SMA period
- RSI parameters
- MACD parameters
- lookbacks
- thresholds
- FVG parameters
- structure parameters
- other concept-specific settings.

9. CANONICAL NORMALIZATION

Audit aliases such as:

EMA 20
20 EMA
EMA(20)
EMA period 20
Price crosses above EMA 20
Price crosses below EMA 20

Ensure they normalize consistently into the existing executable EMA/crossing representation.

Do the equivalent generic normalization for other supported concepts.

10. BUILD WITH AI DRAFT

The draft shown to the user must accurately represent what the AI actually generated.

Do not display a clean-looking draft while hidden conditions are being added later.

Before the draft is presented:

- normalize conditions
- validate compatibility
- identify unsupported concepts
- remove accidental/unrequested conditions
- preserve genuinely requested unsupported concepts as review-required
